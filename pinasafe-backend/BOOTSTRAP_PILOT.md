# Secure Pilot Bootstrap

`bootstrap:pilot` is a manual operator command for a new isolated PinaSafe pilot database after all repository migrations are applied. It is not imported by the server and is not part of startup, build, test, install, or Render lifecycle. The database enforces one-time execution: concurrent calls serialize on a transaction-scoped advisory lock, and a successful rerun is refused.

Apply migrations through `20260928000100_reconcile_users_must_change_password.sql`, B4's emergency-report binding migration, and `20260929000100_create_atomic_pilot_bootstrap.sql`. Independently verify the target and never run this against a legacy project.

Required non-secret configuration names are `DB_BOOTSTRAP_TARGET` (exactly `pinasafe-production-new`), `DB_BOOTSTRAP_EXPECTED_PROJECT_REF`, `SUPABASE_URL`, `DB_BOOTSTRAP_CONFIRMATION`, `DB_BOOTSTRAP_RESCUE_NAME`, `DB_BOOTSTRAP_RESCUE_CONTACT_NUMBER`, `DB_BOOTSTRAP_FIRE_NAME`, `DB_BOOTSTRAP_FIRE_CONTACT_NUMBER`, `DB_BOOTSTRAP_RESCUE_ADMIN_EMAIL`, `DB_BOOTSTRAP_RESCUE_ADMIN_NAME`, `DB_BOOTSTRAP_FIRE_ADMIN_EMAIL`, and `DB_BOOTSTRAP_FIRE_ADMIN_NAME`. Optional: comma-separated `DB_BOOTSTRAP_LEGACY_PROJECT_REFS`. Project refs are trimmed, validated as tokens, and canonicalized to lowercase before exact comparison; malformed legacy-list entries are refused.

Provide `SUPABASE_SERVICE_ROLE_KEY` through the normal server-side secret mechanism. Run from `pinasafe-backend` with `npm run bootstrap:pilot` in an interactive TTY. Non-TTY password entry is refused. Passwords are prompted with echo disabled, validated against the application minimum of six characters, and hashed only in memory with bcrypt cost 12. Terminal raw/paused state and prompt listeners are restored/removed on success, cancellation, or input failure. Never pass passwords as arguments or store them in files.

The URL must be exactly `https://<project-ref>.supabase.co`; a single trailing `/` is also accepted. Empty userinfo/query/fragment delimiters, ports, non-root paths, and lookalike hosts are rejected before the Supabase client is constructed. The project ref must match the expected ref and explicit confirmation. Schema and conflict checks happen before hashing or writes. Database validation repeats the critical input and conflict checks after serialization; PostgreSQL boundary normalization covers spaces, tabs, newlines, carriage returns, form feeds, and vertical tabs to prevent whitespace-based direct-RPC bypass. Any mismatch, missing schema, duplicate input, existing organization/admin, prior completion marker, or partial state refuses without upsert or automatic cleanup. A failed transaction rolls back the marker and all four records together; investigate any existing partial/conflicting state manually. The atomic transaction creates exactly two active organizations (`rescue` and `fire`) and one `admin` user linked to each; it creates no other records.
